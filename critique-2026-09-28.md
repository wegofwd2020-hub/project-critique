## Resolved Since v1.8

### ✅ CSP and HSTS now shipped

**Previously:** §5 Gaps — "No Content Security Policy (CSP) or HSTS verified."

`web/next.config.ts` now applies a full security header block to all routes:
- `Content-Security-Policy`: `default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` — solid baseline
- `Strict-Transport-Security: max-age=31536000; includeSubDomains` (HSTS 1-year)
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/microphone/geolocation restricted to none)

This closes the long-standing v1.8 §5 gap. The P2 action "Verify CSP/HSTS in nginx/ALB configuration" can be retired for the web tier.

**Residual (see New Issues §1 below):** `script-src` contains `'unsafe-inline' 'unsafe-eval'` unconditionally; the Dockerfile introduces `NODE_ENV_FOR_CSP` as a claimed toggle but `next.config.ts` never reads it — the production `script-src` is as permissive as the dev build.

## New Issues Since v1.8

### §N1 — CSP `script-src` always includes `'unsafe-eval'` (HIGH)

**File:** `web/next.config.ts:24–26` / `web/Dockerfile:34–38`

The Dockerfile defines `ARG NODE_ENV_FOR_CSP="development"` and documents: *"Set to 'production' when building for production to disable 'unsafe-eval'."* The commit message says "fix: web CSP header conditional on build-time NODE_ENV_FOR_CSP arg." However, `next.config.ts` **never reads `NODE_ENV_FOR_CSP`**. The `script-src` directive always emits `'unsafe-eval'`, regardless of build mode. A note in the code acknowledges this: *"nonce-based CSP is the correct long-term fix but is left for a dedicated hardening sprint."*

The CSP as shipped is a meaningful improvement over nothing, but the `'unsafe-eval'` exposure is elevated for a platform serving minors, and the Dockerfile documentation actively misleads: a future operator passing `NODE_ENV_FOR_CSP=production` will believe they've hardened the CSP when they have not.

**Action:** Either (a) implement the `NODE_ENV_FOR_CSP` conditional in `next.config.ts` so `'unsafe-eval'` is omitted in production builds, or (b) remove the misleading Dockerfile ARG and comment until the nonce-based hardening sprint ships.

### §N2 — `web/Dockerfile.production` referenced but does not exist (MEDIUM)

**File:** `web/Dockerfile:45`

The comment reads: *"See: web/Dockerfile.production for the secure production runtime."* That file does not exist. Any operator following the comment to find the hardened production Dockerfile will find nothing. The current `web/Dockerfile` runs the web container in `NODE_ENV=development` with `npm run dev` and fail-open Auth0 — correct for local demo use, but there is no shipped production-grade alternative.

**Action:** Either create `web/Dockerfile.production` (a multi-stage build that runs `npm run build + node server.js` with `NODE_ENV=production` and non-root user as the comment describes) or update the comment to remove the forward reference.
