## Newly shipped (this window)

### ✅ FIXED — Hardcoded super-admin default password removed from `seed_super_admin.py` (PR #516, 2026-07-25)

**Severity: high (live credential exposure).** `seed_super_admin.py` defaulted `SUPER_ADMIN_PASSWORD` to `"Admin1234!"` when the env var was unset. `scripts/demo/seed.sh` (the demo orchestrator) ran the script without setting the variable, so any demo seeded via `seed.sh` provisioned the super-admin account `wegofwd2020@gmail.com` with a **publicly-documented weak password** on the **internet-facing admin login** at `demo.usestudybuddy.com` (`POST /api/v1/admin/auth/login`).

**Fix:**
- `seed_super_admin.py` now **requires** `SUPER_ADMIN_PASSWORD` — no default. Rejects empty, <12 chars, or known-weak/leaked values (including the old `Admin1234!`). Fails closed with a clear message.
- `seed.sh` now auto-generates a cryptographically strong password and writes it to a `chmod 600` one-shot file when `SUPER_ADMIN_PASSWORD` is unset, preserving the demo workflow without any hardcoded secret.
- `DEMO_LAUNCH_PLAN.md` updated to remove the old default.

**⚠️ Critical open follow-up: live credential rotation.** The PR commit message explicitly states: *"Operational rotation (live demo) tracked separately — this only closes the code hole so a known password can never ship again."* If the live demo was seeded with the old default, `wegofwd2020@gmail.com` on `demo.usestudybuddy.com` may still authenticate with `Admin1234!`. Rotation requires: `SUPER_ADMIN_PASSWORD='<strong>' python scripts/seed_super_admin.py` against the live DB (UPSERT resets the hash). **This is the single most urgent open action this week.**

**Scope note.** PR #516 covers only `seed_super_admin.py` and `seed.sh`. PR #511 (shipped last week) already made `seed_demo_test_account.py`, `setup_dev.py`, and `seed_phase_a_dev.py` env-overridable. The PR #516 commit message flags one remaining gap: `vm-localhost-bootstrap.sh` still contains dev-only defaults (`DevAdmin1234!`) — lower severity (localhost only), but worth the same treatment.

### ✅ FIXED — `sb_celery_queue_depth` Gauge re-registration bug (PR #519, 2026-07-25)

**Severity: medium (silent metric loss).** `poll_infra_metrics` (Celery Beat, fires every 30 s) constructed the `sb_celery_queue_depth` Prometheus `Gauge` **inside the task body**. `prometheus_client` registers a metric at construction time, so the second poll onward raised `ValueError: Duplicated timeseries in CollectorRegistry`. The task caught this as `metrics_poll_failed` and returned `None` — meaning `sb_celery_queue_depth` was collected **exactly once per worker lifetime** (at first poll), then silently stopped. This was observed on the demo worker.

**Fix:** Move the `Gauge` to `core/observability.py` alongside all other module-level metrics (`db_pool_connections`, `redis_connected`, …). The task now imports and calls `.labels().set()`. Module import is once-per-process — no re-registration.

**Diff:** 2 files, +9/−7 lines. Mechanical move; no behavior change beyond fixing the registration. Lazy import inside the task avoids circular-import risk (observability doesn't import `auth.tasks`).
