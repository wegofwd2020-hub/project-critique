## What changed

### ❌ SECURITY — Next.js 16.3.0 → 16.3.4 patches unauthenticated RCE (#738)

**`fix(deps): bump next 16.3.0 → 16.3.4 for the unauthenticated RCE`** — Two CVEs were present in Next.js 16.0.0–16.3.2:

- **GHSA-2xp9-vwfh-vxw4** (CRITICAL) — Unauthenticated RCE via the Image Optimization API when AVIF files are processed. The commit explicitly notes this **does apply** to the demo: "the demo is Linux-hosted and serves a school's student records."
- **GHSA-p293-qw3h-jr36** — Unauthenticated RCE on Windows-hosted servers (does not apply).
- A high-severity `sharp < 0.35.4` advisory (libheif: GHSA-g89c-p67h-r497, GHSA-2jg2-4ch7-h545) also resolved.

`npm audit --omit=dev --audit-level=high` (which runs in the Frontend Lint & Typecheck CI job) had been **red on `main` and on every open PR, including docs-only ones** before this fix. The RCE was live for an unknown period on a deployment serving student educational records.

**Assessment:** Fixed, but the detection path deserves the same post-mortem note as the Anthropic SDK break in v2.6 (#726): a P0 security advisory was present in a dependency that CI was correctly flagging, yet it persisted on the default branch. The pattern (CI red → ignored until it also blocks something else) is worth addressing at process level, not just patching the instance.

### ✅ NEW — Two new student-level alert types: `student_stuck_on_unit` and `inactive_students` (#737, #743; migrations 0070, 0071)

**`feat(reports): alert when one student cannot get through a unit`** (migration 0070, `stuck_student_alerts`):
The first alert type that is **student-grained** rather than unit-grained. Previous alert types all ran `GROUP BY unit_id`, consuming `student_id` inside `COUNT(DISTINCT …)`, so the evaluator was structurally unable to fire on a named student. This commit introduces the `student_stuck_on_unit` type, triggered when a student's failed-attempt count on a single unit exceeds `report_alert_settings.stuck_attempts_threshold` (default 3, new column). The dedup index is **split**: `uq_report_alerts_open_unit` is narrowed to `alert_type='pass_rate_breach'`; the new type gets `uq_report_alerts_open_stuck` keyed on (school, student, unit). This is correct — a shared unit-only key would collapse two students stuck on the same unit into one alert and silently suppress the second (CLAUDE.md pitfall #35/0066 pattern). Origin: real tester (Venki, 2026-09-02) asking why Attempt #11 · Score 3/8 did not fire an alert.

**`feat(reports): alert when a student stops working, and retire two dead knobs`** (migration 0071, `inactive_student_alerts`):
`inactive_days_threshold` had been configurable since migration 0010 and read by nothing (the evaluator SELECTed it and never referenced the value, per CLAUDE.md pitfall note at migration 0071). Now implemented. Fires when a student has had no lesson view and no quiz session for N days (default 14), measured from `added_at` rather than epoch (to avoid alerting on newly-enrolled students who haven't had a chance to log in). Dedup key `uq_report_alerts_open_inactive` is on (school, student) — no `unit_id`, which the CLAUDE.md note flags as the "0066 trap" — correct because inactive is a student-state alert with no unit reference. New migration also **retires** `score_drop_threshold` and `feedback_count_threshold` from the API and settings form (columns retained with NOT NULL defaults): these were the two other thresholds settable since 0010 but never read. Retiring three-never-read knobs at once reduces the settings-form surface credibly.

### ✅ NEW — "Up next" reading-time estimate is now dynamic (#742)

`fix(student): estimate "Up next" from the lesson, not from a literal` — `_build_dashboard` had `"estimated_minutes": 20` as a literal constant for every unit in the product: a 200-word lesson and a 3,000-word lesson both told the student "about 20 minutes." The fix adds `backend/src/core/reading_time.py` with a reading-speed model based on actual word count (adult reading speed with a grade-scaled factor from Grade 5 → Grade 12). Adds `backend/tests/test_reading_time.py`.

Two evidence-based alternatives were explicitly **rejected**: `estimated_duration_minutes` from the pipeline (present on 250/253 real lesson files; took exactly 3 values — 40/45/50 min — because it is a teacher-facing class-period estimate, not a student reading estimate) and `lesson_views.duration_ms` (too sparse on the demo, and read from a different student's history). The word-count model is estimated from the actual lesson in the content store rather than an aggregate.

### ❌ PIPELINE — `build_unit.py` never wrote DB rows; content was invisible to review→publish flow (#752)

`fix(pipeline): record a per-unit build in the database` — `build_unit.py` performed **no database writes at all**. Every single-unit rebuild produced content on disk while leaving `curriculum_units` and `content_subject_versions` entirely untouched. The acute consequence: `check_content_published` in `backend/src/content/service.py` is on the serving path and returns 404 unless a `content_subject_versions` row with `status='published'` exists for that `(curriculum_id, subject)`. Content produced only by `build_unit.py` would therefore be **unservable** — the review→publish flow could never reach it. The only reason the C-5 regen content (#745, 29 units of `default-2026-g11-science`) was servable at all is that an older `build_grade` run had left v1 rows behind.

**Fix**: `pipeline/db_writes.py` is introduced as the single home for all pipeline DB writes (both entry points previously held their own copies, causing a circular-import hazard if shared via either). `build_grade` delegates to it (behaviour unchanged). `build_unit` now writes to the open pending version (if one exists) or opens a new one. Tests: `backend/tests/test_pipeline_db_writes.py`.

**Assessment:** This was a latent correctness hole in the pipeline's core contract. The C-5 regen that motivated migration 0069 was rescued by accident (stale rows). Any school that had adopted a platform curriculum and then run `build_unit.py` to regenerate a single unit would have had content on disk that was forever invisible to their review workflow. Rated **new gap, now fixed**; but the detection path (the fix was triggered by a specific regen run, not a failing test or monitor) is worth noting.

### ❌ PIPELINE — Prompt had a JSON-invalid `\$` currency instruction; silently losing Accountancy units (#749)

`fix(pipeline): stop instructing the model to emit a JSON-invalid escape` — `_FORMATTING_GUIDELINES` instructed the model to write `\$` for currency amounts inside prose (intending "backslash-escaped dollar sign"). The string was a regular Python triple-quoted string, not a raw string, so `\\$` collapsed to `\$` before the model saw it. The model obeyed the instruction; its response contained `\$`, which is not a valid JSON escape (`\" \\ \/ \b \f \n \r \t \uXXXX` are the only valid ones). `json.loads` failed; the 3-retry loop repeated the identical instruction; `_generate_and_validate` marked the unit failed while `build_grade` still exited 0.

**Impact**: Two units lost silently in the C-5 regen (G11-ACC-001 `quiz_set_2`, G12-ACC-002 `quiz_set_1`). Only Accountancy was affected because it is the only currency-dense subject. The fix: change `\\$` to `$` — dollar signs need no escaping in plain prose.

**Assessment:** A case of the **prompt itself generating malformed content**. The fix is correct and minimal. The broader concern — that `build_grade.py` exits 0 while individual units have silently failed — is a standing observation from v1.4 and earlier ("never write malformed content," per pipeline rules). The 3-retry behaviour exhausts on the same corrupted instruction before failing, rather than detecting the systemic source.

### ❌ DEMO — sync-content.sh cache invalidation had never run — two cascading faults (#748, #750)

Two commits fix a single deployment-correctness gap introduced when `sync-content.sh` shipped:

**#748** (`fix(demo): sync-content must invalidate the VPS content cache`): After rsyncing content files to `/data/content`, the script stopped. `get_content_file` caches every content JSON in Redis under `content:{curriculum_id}:{unit_id}:{filename}` with TTL 3600. Without invalidation, a student could see a mix of old and new units for up to an hour post-sync.

**#750** (`fix(demo): make sync-content's cache invalidation actually run`): The step added in #748 had **two independent bugs** that together meant it had never run on any real sync execution, only silently reported failure: (1) a shell quoting error in the password scrub (`tr -d` line with mismatched quotes) caused remote bash to exit before any command ran; (2) the HTTP response body check compared an empty string against a non-empty response, so even when the remote exec worked, the outer script was asserting the wrong condition.

**Assessment:** A new feature (#748) added a cache-invalidation step, and it was immediately broken in two independent ways — neither caught in any test or dry-run before reaching the demo. The failure mode was a silent "cache invalidation failed" report that looked like a transient network error, not a permanent bug. Demo users saw a content mix on every sync since the feature shipped.
