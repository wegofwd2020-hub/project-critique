## Resolved Since 2026-10-05

### ✅ Epic 2 P1 — Platform is now deployed outside local Docker (PARTIAL)

The headline change of this window. `deploy-demo.yml` (`.github/workflows/`) is a full CI/CD pipeline that fires on every push to `main`:

1. Builds `studybuddy-api` and `studybuddy-web` Docker images tagged by short SHA and pushes to GHCR.
2. SSHs to a VPS at `demo.usestudybuddy.com`; does a `git pull`, pre-pulls images by SHA, and runs `docker compose up -d --pull=never`.
3. Force-recreates `nginx` on every deploy to avoid stale bind-mount inode and upstream-IP cache issues.
4. Waits up to 120 s for `/healthz` to return 200 (replaces the prior `sleep 30` that caused a false-red incident in August, #687).
5. Verifies the running app is serving **this exact commit** — API's `/api/v1/health.build` and web's `/build-id` are compared against the `SHORT_SHA` that was built — directly addressing the #583 failure mode (stale box reporting success).
6. Runs `scripts/demo/smoke.sh` against the public URL; on failure, auto-opens a `priority:high / incident:demo` GitHub issue.

The 16+ deploy-workflow fix commits in this window reflect active commissioning rather than design churn: env-file passing to work around sudo's `env_reset`, SSH session consolidation to eliminate a timing race on the env file, `--pull=never` to prevent Compose v5.6+ re-pull clobbering the pre-pulled image, and stale GHA mode=max cache busting for `BUILD_ID` injection.

**What this resolves:** The "platform has never run outside local Docker" finding that has been P1 for 5+ windows is no longer true. `demo.usestudybuddy.com` is live.

**What remains open:** This is a single-VPS Docker Compose deployment, not the managed Postgres/Redis/CDN/K8s architecture Epic 2 G-1 describes. G-4 observability dashboards remain blocked. Treat this as "demo deployed" not "production-ready infrastructure". The P1 downgrade is from "has never run externally" to "VPS demo live; prod-grade hosting TBD".

Creates a fully self-contained `smoketest-{run_id}` school with a teacher (grades 9–12), 4 students (G9–G12), 4 classrooms with curriculum packages; runs super-admin, teacher, and student persona checks; tears down all fixtures in a single invocation.

This fills the gap between the `quiz_suite` (live-stack, excluded from CI) and the Playwright suite (real-browser E2E) — a persona-level integration harness that can run on demand against any deployed environment.

**Note:** `persona_smoke.py` has no dedicated test file. The `DELETE /admin/test-schools/` endpoint is only validated by the smoke harness itself; no unit test covers the name-guard branch or FK teardown order.

## New Risks Introduced

### ⚠️ `DELETE /admin/test-schools/` endpoint: name guard is the only production safeguard

The name check (`name.startswith("smoketest-")`) is correct for its stated purpose, but the guard is a string prefix on a mutable field. A school named `smoketest-RealSchoolName` by accident or by a confused super-admin would pass the guard. Consider: (a) a separate boolean `is_test_school` column set at creation time rather than checked by name, or (b) restrict the endpoint to `APP_ENV ∈ {development, staging}` so it is unreachable in production regardless of name.

### ⚠️ CI/CD pipeline is deploying to a single VPS with no rollback automation

`deploy-demo.yml` deliberately does not auto-rollback on smoke failure (the workflow's inline comment states: "Auto-rollback is intentionally not wired — the operator should triage and decide"). This is the correct safety posture for a demo environment. However, the rollback runbook referenced (`docs/DEMO_LAUNCH_PLAN.md §2`) should be verified to exist and be current before the next failed deploy.

### ⚠️ GITHUB_TOKEN used for `git pull` on VPS — rotates on every run

The VPS `git pull` authenticates via a `GITHUB_TOKEN`-derived credential written to a temp file (correctly cleaned up after). `GITHUB_TOKEN` is ephemeral per-run, so there is no persistent secret on the VPS, which is correct. Verify that the temp file cleanup runs even on SSH failure (it is inside a `&&` chain and will not execute if the `git` step fails).
