## New Since v1.8

### ❌ [NEW, CRITICAL] Live credentials committed to git — `VENKI_TESTING_2026-10-07.md`

`VENKI_TESTING_2026-10-07.md` is tracked in git (committed at `eec5bdb`) and contains:

- Admin password for `demo.usestudybuddy.com/admin/login`: plaintext in the file
- Shared teacher password: plaintext in the file
- Shared student password: plaintext in the file

This is a credential-in-repo incident, following the same pattern as `DEV_ACCOUNTS.md` (flagged v1.2, resolved via git tag). Now with a deployed environment behind these credentials, the risk class is higher. Whether or not the repo is public, any CI secret scanning, archive, or fork propagates these. The file should be removed from git history (`git filter-repo`) and credentials rotated. `LOCAL_DEV_LOGINS.md` and `LOCAL_DEV_LOGINS_VAGANAM.md` (also tracked in git) contain local dev passwords — lower risk (localhost only) but same pattern.

**Action:** (1) rotate `demo.usestudybuddy.com` admin/teacher/student passwords immediately; (2) remove `VENKI_TESTING_2026-10-07.md` (and review `LOCAL_DEV_LOGINS*.md`) from git history; (3) add `*TESTING*.md` and `*LOGINS*.md` patterns to `.gitignore`; (4) re-examine why nightly-secrets-scan (`nightly-secrets-scan.yml`) did not flag these.

### ✅ [NEW STRENGTH] Persona smoke harness — third test tier

`scripts/smoke/persona_smoke.py` (2 PRs: `c9bd2e1`, `045de02`) is an on-demand HTTP smoke harness that:
- Creates self-contained fixtures via the API (1 school, 1 teacher, 4 students per grade 9–12, 4 classrooms, 4 classroom-student assignments)
- Runs persona checks against any URL (`--url http://127.0.0.1:8001` or `--url https://demo.usestudybuddy.com`)
- Tears down all fixtures on exit (or `--no-teardown` for debugging)
- Writes JSON + Markdown reports to `reports/smoke/` (gitignored)

This is the third test tier: unit/integration (pytest) → live-stack (quiz_suite) → persona smoke (this). It can catch regressions on the deployed VPS before or after CI, and the self-contained fixture strategy avoids the seed-state fragility that has plagued earlier live-stack tests. Worth documenting in `AGENTS.md`/`studybuddy-practices.md`.

### ⚠️ [NEW GAP] Backup/restore Phase 2 gap — DB schema not captured

`CHANGES.md` (2026-09-26) documents a live-verified finding: `backup-all-grades-content.sh` captures only `content.tar.gz` (the file store). When a curriculum's DB records (`curricula`, `curriculum_units`) are deleted and a restore is run, files come back but curriculum rows are absent — the restored content is unreachable without manual DB re-entry.

A Phase 3 enhancement is needed: include `pg_dump` of the affected `curricula` + `curriculum_units` rows in each grade backup, and import them on restore. Until this lands, the Epic 15 backup/restore story is file-complete but DB-incomplete. Raise this to P2 — it blocks the restore guarantee that Epic 15 advertised.

### ⚠️ [OBSERVATION] CI/CD deploy pipeline stabilized after ~15 fix commits

The deploy workflow took 13 dedicated fix commits to stabilize (`eec5bdb` through `3da84d6`) covering: SHA-tagged GHCR images, env-file race conditions, restricted deploy user, GHCR token handling, Docker Compose v5.6.0 pull policy, disk prune, and build-cache busting. This is normal for a first deploy pipeline, but the iteration history suggests the VPS environment's state was not well-understood before the workflow was written. A deploy runbook (`scripts/demo/DEPLOY_RUNBOOK.md` or in `OPERATIONS.md`) documenting the key gotchas (image tagging convention, deploy user restrictions, env-file race, smoke failure path, rollback) would prevent future regressions.

### ⚠️ [OBSERVATION] Epic 2 doc is stale

`EPIC_02_production_launch.md` still reads "No production deployment exists yet" and "No CI/CD pipeline beyond local test runs." Both statements are now false. The doc should be updated to reflect the VPS demo deployment and the working `deploy-demo.yml` workflow, and G-1's status should be revised to reflect partial completion.
