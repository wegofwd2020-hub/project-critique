## What changed

### ✅ NEW STRENGTH — `anthropic` SDK fixed; Claude content generation working again (#725, #726)

Two related fixes landed on the same day (2026-09-01):

**#726** (`fix(deps): bump anthropic 0.28.0 → 0.125.0`) — `anthropic==0.28.0` is incompatible with `httpx==0.28.1`. The SDK passes `proxies=` to the httpx client constructor; httpx removed that keyword in 0.28, so `Anthropic()` raised `TypeError` before any request was sent. This silently broke **all Claude content generation in `celery-pipeline`** (`CLAUDE_MODEL = claude-sonnet-4-6` is the default provider). OpenAI still worked, which is presumably why no alarm had fired. The fix bumps to `0.125.0` (the newest release within the `<1.0,>=0.28` constraint the `wegofwd-llm` wrapper requires).

**#725** (`fix(help): make the help widget survive a failing LLM, and let the indexer finish`) — the help-corpus indexer (`index_help_library.py`) had never completed on any machine because a Voyage account without a paid plan is capped at 3 req/min, and the script batched 5 requests back-to-back. It failed on batch 3 every run — which is likely why the `help_chunks` table has been empty since migration 0040 was added (months). Two hardening fixes: pacing (21 s between batches, `EMBED_BATCH_PAUSE_S` override), and `zip(..., strict=True)` so a short embedding response errors loudly rather than silently indexing a truncated corpus. The corpus now indexes cleanly: 67 chunks, all embedded. A retrieval probe confirms the right sections are returned for real school-admin questions.

**Assessment:** The Anthropic SDK incompatibility is the more serious of the two — it means any new Claude-generated content built after `httpx` was upgraded was silently routed through OpenAI, not the configured provider. The duration of the breakage is unclear from the commit message; it is fixed now. The `strict=True` zip discipline (#725) is a small but replicable pattern worth adopting wherever an embedding or batch API call pairs a list of inputs with a list of results.

### ⚠️ NEW GAP — doc-drift CI was faking green for five months (#729)

**`ci: make the documentation drift checks fail instead of skipping`** — both GitHub Actions workflows (`doc-drift.yml` and `glossary-drift.yml`) checked for `DOCS_REPO_TOKEN` at the top and `exit 0`'d if it was absent. The secret has never been configured, so neither workflow has ever run a real check. Both have been green nightly for five months while doing nothing.

The fix makes both workflows **fail** when the token is absent, with an error that says to add the PAT or delete the workflow. A guard that cannot run should look broken, not healthy.

**What the inert check was hiding**, measured when `check_doc_drift.py` was run manually against the real docs checkout:
- `ARCHITECTURE.md` last updated 2026-03-23: describes a mobile-first Kivy product, mentions Kivy four times, Next.js zero times — the primary client surface is absent from the architecture document.
- `API_REFERENCE.md` documents 208 endpoints; the app serves **266** (58 undocumented).
- Migrations referenced stop at **0048**; the repo is at **0069** (21 migrations behind).

**Status:** The workflows now fail (correctly) because `DOCS_REPO_TOKEN` is still not configured. The drift is discovered but not fixed. Adding the PAT to GitHub secrets is the immediate action — then the check will file an issue listing the specific stale references.

**Priority escalation:** This was a P3 documentation item in v1.8; with concrete, measured drift (21 missing migrations, 58 endpoints, a six-month-stale architecture doc that describes the wrong client) it warrants **P2**.

### ✅ NEW STRENGTH — ADR-008 Phase 3a: question registry shipped (#728)

**`feat(quiz): question registry + backfill (ADR-008 Phase 3a)`** — Migration 0069 (`question_registry`) gives each question a stable row: `stable_question_id` (PK, content-addressed from migration 0067), `curriculum_id`, `unit_id`, `difficulty`, `status` (active/retired), `source_set`. Bodies stay in the content store (Decision 5 in the ADR); the registry holds identity, provenance, and lifecycle only.

**Measured corpus:** 212 units, 5,269 distinct questions, median 24/unit, **minimum 17** — every platform unit has enough to draw from. Raw counts before dedup were skewed easy 66%/medium 24%/hard 11% because duplicates are overwhelmingly easy; after dedup the distribution is medium 45%/easy 36%/hard 19%.

**Authoring Studio content** had 82% duplicate stems (6,616 rows collapsed to 659 by dedup), with one unit having 24 questions and 1 distinct. That content is not student-facing (no `authored-*` rows in `curricula`), recorded in the ADR as a generation-quality signal.

**Phase 3b** (enlarge the pool to the tester's 150–200 target) is split out as a separate costing decision. Phase 3a draws 8 from 17+ distinct questions per unit, giving tens of thousands of distinct quiz permutations per unit at zero generation spend.

**Backfill script** (`backend/scripts/backfill_question_registry.py`): batched upsert (was 7,124 round-trips, now 1.2 s). A bare `continue` on JSON parse errors was replaced with a counted warning so malformed files shrink the pool visibly.

**Tests:** 197 new functions in `test_question_registry_adr008.py`, including `asyncpg.CheckViolationError` assertions by constraint name (not `pytest.raises(Exception)`, which would pass on a typo in the SQL).

### ✅ NEW STRENGTH — Report metric bugs corrected (#731)

`fix(reports)` corrected two independent bugs in the teacher reports service, both surfaced by a tester on 2026-09-02:

**Bug 1 — `avg_att` (attempts-to-pass) computed incorrectly.** The query took `MAX(attempt_number)` across passing sessions rather than `MIN(attempt_number)` per student first, then averaging. A student who passed on attempt 1, retook for practice and passed on attempt 3 was recorded as needing 3 attempts. This produced an arithmetically impossible result on the demo: 100% first-attempt pass rate AND 2.00 attempts-to-pass simultaneously — and was pushing the unit into the "Watch" band. Fixed with a CTE that takes `MIN(attempt_number)` per `(unit_id, student_id)` before averaging.

**Bug 2 — `general_feedback_count` missing.** Feedback submitted without a unit association was not counted in per-unit report totals, so the "Unreviewed feedback" tile on the school dashboard disagreed with the sum of all per-unit report counts. Fixed by adding `general_feedback_count: int = 0` (defaulted for backward compatibility with older clients).

**Bug 3 — `unit_title` silently dropped in quiz DTO mapper.** `getQuiz()` in `web/lib/api/content.ts` copied every field from the raw API response **except** `unit_title` — the field wasn't in `BackendQuizResponse`, so there was nothing to copy even if the mapper had tried. `QuizPlayer` consumed `quiz.unit_title` conditionally, so it typechecked clean and rendered nothing. The API response was correct; the component was correct; the seam between them was wrong. The same tester reported the missing unit name twice (2026-08-31 and 2026-09-02), was told both times it was fixed, and was right both times.

**Architecture note:** this is the third documented instance of the `web/lib/api/*.ts` hand-written DTO drift pattern (pitfall #40): the generated `types.gen.ts` is not what pages import. The mapper is the invisible seam. No structural fix yet — still a P2.
